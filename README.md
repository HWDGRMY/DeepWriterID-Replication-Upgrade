# DeepWriterID Replication & Upgrade

**仓库名：`DeepWriterID-Replication-Upgrade`**

> 对论文 [*DeepWriterID: An End-to-end Online Text-independent Writer Identification System*](https://arxiv.org/abs/1508.04945)（Yang et al., 2015）的逐条对齐复刻，并在 CASIA-OLHWDB 2.0–2.2（1019 位书写者）上完成双骨干对照实验与评测可信度验证。

本仓库是这一系列工作的**最终修正版**。

## 关于旧仓库

本仓库取代以下两个早期仓库：

| 仓库 | 内容 | 当前状态 |
| :--- | :--- | :--- |
| DeepWriterID-Replication（v1.0） | DCNN 基线，页面级 95.09% | **已转为私有仓库（Private）** |
| DeepWriterID-v2（v2.0） | ConvNeXt V2 升级 + 拐点阈值修复 | **已转为私有仓库（Private）** |

## 2. 结果解读与适用范围

以上数字若不加说明，容易产生两种相反方向的误读：一是将 99% 视为可与原论文直接对标的结论，二是将 21% 视为训练失败。本节说明其确切含义与适用边界。

### 2.1 不得与原论文的 95.72% 直接比较

三项协议差异，且方向均有利于本仓库：

| 维度 | 原论文 | 本仓库 | 影响 |
| :--- | :--- | :--- | :--- |
| 训练页/书写者 | 2 | **4** | 本仓库的注册数据多一倍 |
| 测试页内容 | **固定内容**（全部书写者抄写同一篇文章） | **自由内容**（书写者本人的第 N 页） | 论文只能依赖笔迹风格；本仓库的测试页与训练页出自同一次书写 |
| 语料 | NLPR DB I | CASIA-OLHWDB 2.0–2.2 | 采集条件不同 |

**唯一可与本仓库直接相减的参照是 v1.0 的 95.09%**，因为二者使用同一份 `metadata.csv`、同一批 1019 页测试集与同一份评测代码（已逐字节验证，见 [§8.1](#81-评测代码与-v10-逐字节一致)）。

### 2.2 页面级准确率主要由聚合过程决定

论文的做法是：将一页中全部伪字符的 softmax 输出按类别取平均，再取 argmax。本数据集中每页约有 **283 个伪字符**，因此该指标对参与聚合的样本数高度敏感：

| 每页参与聚合的伪字符数 K | 页面级准确率 |
| ---: | ---: |
| **1** | **19.57%** |
| 2 | 30.95% |
| 5 | 48.83% |
| 10 | 66.97% |
| 20 | 83.16% |
| 50 | 95.45% |
| 100 | 98.12% |
| 283（全部） | 99.41% |

K=1 时仅为 19.57%，与伪字符级准确率基本相当。由此可知，99.41% 的来源并非"逐字识别准确"，而是"单字准确率约 20%，整页 283 个字共同投票"。

这正是 DeepWriterID 方法的核心价值所在；同时也意味着：**页面级数字主要反映聚合效率，伪字符级数字才反映单样本识别能力。** 本仓库同时报告两者。

### 2.3 伪字符级准确率存在固有上限

伪字符级仅 21% 这一事实，容易被认为是训练不充分。实际上该指标难以提升，由任务性质决定：

一页包含 283 个伪字符，每个伪字符仅承载一个汉字（约 32 个采样点、4 个片段）。**单个汉字所含的笔迹信息量，本不足以在 1019 位书写者中唯一确定其身份。** 众多书写者的"永""之""口"等字形高度相似。

以信息量作对照：

| 判定单元 | 可用笔迹量 | 1019 类下的合理准确率 |
| :--- | :--- | :--- |
| 单个伪字符 | 1 个字 / 约 32 点 | **约 20%**（实测 20.8–21.6%） |
| 一页 | 约 283 个字 / 约 9000 点 | **约 99%**（实测 99.4–99.6%） |

二者相差约 10 倍信息量，对应约 5 倍准确率差距。论文采用页面级投票，正是基于单字符不可靠这一前提；反之，若单字符准确率可达 80%，则应怀疑任务过于简单或测试集存在泄漏。

该判断有两个实测侧面：

- **训练集干净 char_acc 仅 30.21%**（测试集 20.18%）。模型对自身训练样本亦仅能识别约三成，说明瓶颈不在拟合程度，而在单字符信息量的固有上限
- **K 曲线**（[§2.2](#22-页面级准确率主要由聚合过程决定)）显示 K=1 时为 19.57%，页面级的 99% 完全来自聚合

> 因此，伪字符级准确率不宜与图像分类领域的常见数值类比。该任务是"一位书写者所写的一个字 → 1019 选 1"，其上限远低于整页识别。评价模型质量应以页面级为准。

### 2.4 20-test 在本数据上未带来增益

| 模型 | 干净单次 | 仅执行 DropSegment（第 1 轮） | 20 轮平均 |
| :--- | ---: | ---: | ---: |
| ConvNeXt | **99.61%** | 99.31% | 99.51% |
| DCNN | **99.41%** | 99.02% | 99.21% |

- DropSegment 使单轮下降 **0.29–0.39 个百分点**（丢失 22.5% 墨迹确实增加识别难度）
- 20 轮平均可挽回约 0.2 个百分点，但**未能恢复至干净水平**
- 净结果为 **−0.10 / −0.20 个百分点**

论文报告 "with DropSegment, all the identification rates are markedly improved"，其基线为 **95.72%**。当准确率达到 99.4% 时仅余 6 页错误，这些均为确实难以区分的书写者，删除笔画只会提高其误判概率。

**结论：DropSegment 在低准确率区间为增益，在高准确率区间则表现为噪声。** 训练阶段仍按论文保留该增强（作为抑制过拟合的正则化手段），测试阶段不执行 20-test 亦可取得更优结果。

### 2.5 测试集被用于模型选择

训练时未单独划分验证集（每位书写者仅 5 页，若再划分验证集会进一步压缩训练数据）。每轮在测试集上评估并保存最佳权重，因此所报告的 99.61% / 99.41% 属于**测试集上的最优选择结果**，存在乐观偏差。

更接近无偏估计的是最后一轮的数值：

| 模型 | 末轮 ep80 | 最佳轮次 | 偏差 |
| :--- | ---: | ---: | ---: |
| ConvNeXt | 99.61%（ep80 亦为最佳） | 99.61% @ep72 | 0 |
| DCNN | 99.41%（ep80） | 99.41% @ep59 | 0 |

本轮训练未出现"最佳轮次显著高于末轮"的情形，两个模型的末轮与最佳基本一致，可认为选择偏差较小。但此结论属于**本次运行的经验事实，不构成方法学保证**。

### 2.6 与 v1.0 的 95.09% 可以比较

v1.0 的 95.09%（969/1019）与本仓库使用完全相同的划分文件与测试集，且该成绩是在**数据流存在缺陷**的条件下取得的：

| 缺陷 | 后果 |
| :--- | :--- |
| **拐点检测阈值与坐标量级不匹配**（`load_wptt_page` 已对坐标乘以 0.1，而 `detect_corners` 的阈值按未缩放量级设定） | 检测不到有效拐点，切分退化为仅按宽度硬切 |
| **伪字符形状退化** | 由论文预期的**方形**退化为**扁行**（宽度远大于高度），每页约 209 个 |
| **DropSegment 从未真正生效** | `get_segments` 同样依赖拐点检测，无拐点则片段数为 1–2，落入跳过条件，增强恒为恒等变换 |

也就是说，v1.0 的 95.09% 是在**论文核心机制 DropSegment 完全失效、且伪字符几何形态偏离论文设定**的情况下取得的。

本仓库修正后，伪字符恢复为方形（高宽比 1.17，落在论文给出的 [1, 1.3] 区间内），DropSegment 实际生效（平均丢弃 19.8% 墨迹），签名通道亦具备真实空间结构。

因此对比成立：

| 流水线 | 伪字符形状 | DropSegment | 页面级（同一测试集） |
| :--- | :--- | :--- | ---: |
| v1.0 | 扁行（宽 ≫ 高） | **未生效** | 95.09% |
| **本仓库 v2.2.1** | **方形（高宽比 1.17）** | **生效** | **99.41%（DCNN）/ 99.61%（ConvNeXt）** |

> 说明：本仓库未用 A0 流水线从零复现 95.09%（该状态下自零训练至 ep36 仅为 58.00%，当时的训练配置已不可考）。95.09% 这一数值本身系真实取得，其对应的数据流缺陷由特征统计数据确证（见 [§5](#5-历史缺陷记录)），故作为对照有效。

## 4. 与论文的对齐：八处修正

本仓库逐段核对论文原文（包括从 PDF 原始内容流还原的表格与被压缩的数学符号），发现并修正了八处偏差。以下逐项列出，并附实测依据。

### #1 切分阈值：由「页高/10」改为「先测量平均字高」

> 论文 §2.2："the **average height** is measured first. Then, each of the segments will be sequentially assigned to form a pseudo character. When the width of a character exceeds the average height after adding a segment, this segment is regarded as the beginning of a new character."
>
> "the height-to-width ratio should be the same. We thus determined **this ratio to be 1** for simplicity … other ratio value between **[1, 1.3]** is also proper"

早期实现以 `page_height / 10` 作为平均字高的代理值（隐含假设一页恰好排布 10 行字）。

**实测（25 页）：代理值中位为 34.4，真实平均字高中位为 19.3，偏大约 1.78 倍。** 其后果是伪字符高宽比仅 0.70，**落在论文给出的 [1, 1.3] 区间之外**。

改为先测量后切分的结果：

| | 阈值 | 高宽比中位 | 每页伪字符数 |
| :--- | ---: | ---: | ---: |
| 修正前 | 34.4 | 0.70 | 260 |
| **修正后** | **19.3** | **0.96–1.17** | **531** |

### #2 宽度判定：由「累加各段宽度」改为「包围盒宽度」

> 论文 §2.2："When the **width of a character** exceeds the average height after adding a segment…"

论文所指为"字符的宽度"，即已纳入的全部点合并后的水平跨度。早期实现写作 `current_width += seg_width`，将每个片段**自身**的宽度累加——片段在水平方向大量重叠（偏旁、同一笔往复），累加会重复计数，导致过早断句。

**实测（12 页，真实字符数中位 251）：**

| 实现 | 伪字符/页 | 点/伪字符 | 高宽比中位 | 片段/伪字符 |
| :--- | ---: | ---: | ---: | ---: |
| 累加段宽 | 554 | 15 | 0.97 | 2 |
| **包围盒宽（论文）** | **284** | **32** | **1.17** | **4** |

包围盒实现给出 284 个伪字符，与 251 个真实字符基本对应；高宽比 1.17 亦落入论文认可的 [1, 1.3] 区间。

### #3 几何增强：由图像域改为坐标域，并补足缩放

> 论文 §5："**During the training stage, before the extraction of path-signature feature maps**, we adopted a random mix of affine transformations i.e., **translation, rotation, scaling** as the elastic distortion…"

存在两处偏差：

1. **作用位置**：早期在渲染完成的 64 通道特征图上执行 `RandomRotation` / `RandomAffine`，签名数值实际未发生变化（仅相当于将同一张图旋转）。论文要求变换作用于**坐标**，变换后重新计算的签名方为"变换后路径的签名"。
2. **缺少缩放**：早期仅有旋转与平移，`scale` 参数默认为 `(1.0, 1.0)`，等同于未执行。论文明确列出 scaling。

现实现为 `_augment_points`：绕质心旋转 ±5°、缩放 0.9–1.1、平移 ±5%，`(-1, 0)` 分隔符行原样保留。

> 随机数采用模块级 `np.random` 而非私有 Generator——后者在 `fork` 时会被复制为同一状态，导致各 worker 产生完全相同的增强。

### #4 DropSegment：由「50% 比例」改为论文的固定 m

> 论文 §3："If a character contains **m′ ≥ m** (m′ ≫ m) segments, a **random number r ∈ [0, m]** of the segments will be removed; the removed segments are also randomly chosen. Our DropSegment using this setting not only generates a considerable quantity of samples but also **prevents too much information loss**."
>
> "we would **never remove all** the segments of a character"

早期实现为 `max_remove_ratio=0.5`（删除一半），并附带 `if len(segments) <= 3: return points` 的硬编码跳过门槛。**论文中并无百分比设定，只有固定上限 m。**

修正后的实现：

```python
if n_seg < max_remove:      # 论文条件 m' >= m
    return points
hi = min(max_remove, n_seg - 1)   # 永不删光
remove_count = random.randint(0, hi)   # r ~ U{0..m}
```

实测（m=1）：参与率 76.4%，平均丢弃 **19.8%** 墨迹（旧实现为 38.9%）。

> 与论文仍存的差异：论文举例为"3 笔汉字含 2+3+4 = **9 个片段**"，而本仓库的拐点检测给出中位 **4 个**。此差异不源于 DropSegment 本身，而源于**数据采样密度**——本数据每笔画仅 13.7 个点、每字符 39.9 个点，而典型在线手写为 100–300 点/字符。拐点检测依赖二阶差分，13 个点上最多可靠分辨 1–2 个弯曲。

### #5 路径签名：移除尺度归一化

> 论文 §3："the maps of the first three iterated integrals seem **similar in magnitude** among the writers, while the differences between the maps **beyond the second level k≥2 are appreciable** … **higher levels of the path-signature may contain information that will contribute positively**"

路径签名对坐标尺度敏感：level-n 项的量级约为"路径长度^n"。实测在原始坐标下 level1≈16、level5≈1.3×10⁵，**单条路径内跨越 7 个数量级**。

早期为此引入"中心化 + 除以最大边长"的归一化。然论文明确指出高阶签名更具判别力，尺度归一化将各层压缩至同一量级，恰好抹平了这一结构。现予以移除。

消融实测（24 类过拟合测试，各 2 次运行取较小值）：ConvNeXt 在"仅 4×4 膨胀"时 **12 步**收敛，在"膨胀 + 归一化"时 **16 步**，即移除归一化后收敛更快。

### #6 位图通道：由硬编码改为可配置开关

论文对输入通道数存在两处互相矛盾的表述：

- `"M denotes the number of input channels, which is equal to the number of signature feature maps"`，即 M = 63
- `"the path-signature feature **together with Bitmap** can greatly enhance the network representation"`，且 Fig.4 的消融曲线族为 `Bitmap`、`Bitmap+Sign.1` … `Bitmap+Sign.5`，位图始终参与

按后两处，所提方法为位图 + 签名 = **64 通道**。现实现为 `use_bitmap` 开关（默认 `true`），可切换至 63 通道以复现另一种读法。

> 附带结论：在早期缺陷流水线下，63 个签名通道退化为常数底图，**模型实际等价于论文的「Bitmap baseline」**，而非论文所提方法。修正后签名通道方具备真实空间结构（空间标准差 0.129）。

### #7 分类头 Dropout：由错误的 0.52 恢复至 0.2

原论文 DCNN 的分类头自带 `Dropout(0.2) + Linear`（位于 `self.output` 内），**并不存在"分类头之前额外施加 dropout"这一设计**。早期版本将 ConvNeXt 所使用的 `dropout_classifier=0.4` 一并传入 DCNN，形成 `Dropout(0.4) → Dropout(0.2) → Linear`，**有效 dropout 由 0.2 升至 0.52**。

修正方式为拆分为两个参数，`dcnn_dropout_classifier` 默认为 0，并在冒烟测试中加入逐键比对护栏：

```
[PASS] ★ Dropout 集合与原仓库完全一致（不能多、p 不能变）
      原=[('fc1.2', 0.2), ('fc2.2', 0.2), ('output.0', 0.2)]
      我=[('fc1.2', 0.2), ('fc2.2', 0.2), ('output.0', 0.2)]
```

### #8 伪字符二次切分：由静默丢弃改为拼接

`__getitem__` 会对已切分完成的伪字符再执行一次切分。早期实现写作 `final_points = chars_drop[0]`，即多出的分块被**静默丢弃**。

在"抬笔分隔符被抹平"的早期实现下，该缺陷会大规模暴露：拼接点坐标突变导致拐点检测产生伪角点，二次切分随之裂开。**实测训练集 24.9% / 测试集 22.3% 的样本被截断，平均丢弃 21.9% 墨迹，最坏情况丢弃 95%，而参数量、张量形状与样本数均无异常表现。**

现改为**拼接全部分块**（分块之间插入分隔符），宁可多一个分隔符亦不丢弃数据；同时统计发生率（实测 0.08%）。

以下缺陷在早期版本中经实测确认存在，自 v2.1 起已全部修复。此处记录以说明旧仓库的结论为何不宜沿用。

| # | 缺陷 | 实测证据 |
| :--- | :--- | :--- |
| 1 | 拐点检测阈值与坐标量级不匹配 | 检测不到有效拐点，切分退化为按宽度硬切；伪字符由方形退化为**扁行**（每页约 209 个）；**DropSegment 因此从未真正生效** |
| 2 | 抬笔分隔符被抹平 | 位图 **19% 的墨迹为伪造**（将抬笔前后两点直线相连）；单条伪线段长达 28.7 px，占画布 53%；**34.4% 的字符受影响** |
| 3 | 二次切分静默截断 | 训练集 **24.9%** / 测试集 **22.3%** 样本被截断；中位丢弃 **21.9%** 墨迹，最坏 **95%** |
| 4 | 签名通道退化为常数底图 | 签名通道空间标准差 **0.0176**，位图为 **0.4598**，前者仅为后者的 **3.8%**；63/63 通道近乎恒定 |
| 5 | 62 维签名当作 63 维使用 | 缺少论文定义的 k=0 常值项（论文 §3："when k = 0, the signature is constant at 1"） |

另有一项工程缺陷：

| 缺陷 | 后果 |
| :--- | :--- |
| ConvNeXt 的 stride-4 patchify 与签名单像素点混叠 | ConvNeXt 无法过拟合 24 个样本，loss 停滞于 `ln(24)=3.1780`；引入 4×4 膨胀后解决（阶梯验证：不膨胀 1/3 → 3×3 2/3 → 4×4 3/3） |

### 第 1 项缺陷与 v1.0 的 95.09%

第 1 项缺陷（拐点检测阈值与坐标量级不匹配）是 v1.0 取得 95.09% 时的数据流状态。其连锁后果为：

1. 检测不到拐点，切分退化为仅按宽度硬切
2. 伪字符由论文设定的方形退化为扁行
3. `get_segments` 同样依赖拐点检测，片段数为 1–2，落入跳过条件，**DropSegment 恒为恒等变换，从未真正生效**

因此 v1.0 的 95.09% 是在论文核心机制 DropSegment 完全失效的条件下取得的。本仓库修正后，伪字符恢复方形、DropSegment 实际生效，页面级准确率提升至 99.41%（DCNN）/ 99.61%（ConvNeXt）。详见 [§2.6](#26-与-v10-的-9509-可以比较)。

## 6. 双骨干架构对照

两个骨干网络的输入输出契约完全一致（输入 `(B, 64, 96, 96)`，输出 `(B, 512)` 特征或 `(B, num_classes)` logits），因此对比可排除数据管道差异。

### 6.1 论文原架构 DCNN

严格依论文 §4 实现：

```
64×96×96 → 80C3-MP2 → 160C2-MP2 → 240C2-MP2 → 320C2-MP2 → 400C2-MP2 → 480FC → 512FC → Output
```

| 设计项 | 取值 |
| :--- | :--- |
| 卷积核 | 首层 3×3，其余 2×2，stride 1，**padding 0** |
| 池化 | 2×2，stride 2 |
| 通道数 | 80 → 160 → 240 → 320 → 400（每次递增 80） |
| 全连接层 | 1600 → 480 → 512 |
| Dropout | fc1 / fc2 / output 各 **0.2** |
| 输入布局 | 54×54 位图居中置于 96×96 网格，padding 由边框提供 |

### 6.2 ConvNeXt V2-Femto

| 设计项 | 传统 DCNN | ConvNeXt V2 | 借鉴来源 |
| :--- | :--- | :--- | :--- |
| 卷积核 | 3×3 堆叠 | **7×7 深度卷积** | Transformer 全局感受野 |
| 归一化 | 无 | **LayerNorm** | Transformer |
| 激活函数 | ReLU | **GELU** | BERT / GPT |
| 瓶颈结构 | 先降维后升维 | **先升维后降维（4×）** | Transformer MLP |
| 下采样 | 残差块内 stride=2 | **独立下采样层** | Swin Transformer |
| 通道竞争 | 无 | **GRN 层**（无参数） | ConvNeXt V2 新增 |

**Femto 变体的选择依据**：Atto 3.7 M（1.4 倍）偏小；Femto **5.6 M**（2.1 倍）最为均衡；Pico 9.1 M（3.5 倍）过拟合风险较高；Tiny 28.6 M（11 倍）远超数据规模。

### 6.3 两模型的交叉过程

本轮训练中值得记录的观察之一是：**相对优劣取决于训练预算**。

| 轮次 | ConvNeXt char_acc | DCNN char_acc | 领先方 |
| ---: | ---: | ---: | :--- |
| 1 | 0.47% | **0.60%** | DCNN |
| 10 | 7.74% | **13.16%** | DCNN |
| 30 | 14.94% | **17.29%** | DCNN |
| 50 | 19.28% | **19.42%** | DCNN（几乎持平） |
| **60** | **20.45%** | 20.27% | **ConvNeXt** |
| 80 | **21.60%** | 20.79% | ConvNeXt |

交叉点位于 ep55–60 之间。训练预算在 50 轮以内时 DCNN 更优；至 80 轮 ConvNeXt 反超 0.8 个百分点。前 55 轮 DCNN 始终领先。

**关于 lr 的线性缩放**：

```
progress ∝ (N/B) × lr = (N/B) × (lr0·B/B0) = N·lr0/B0   →  与 batch 无关
```

即线性缩放后，**每轮的学习进度与 batch 无关**，调整 batch 仅改变梯度噪声（较小 batch 噪声更大，通常带来轻微的正则化收益）。另有过拟合实验表明 ConvNeXt 在 `lr ≥ 2e-3` 时失败，`2.5e-4 ~ 5e-4` 区间可正常学习，2.604e-4 落在安全区间内。

### 7.3 关于早停：已从共享管道训练器移除

**`src/training/trainer_multi.py`（即 `configs/multi_arch.yaml` 所使用的训练器）不实现早停。** 早期版本设有 `patience` 机制，现已删除，原因有二，均经实测确认。

> 说明：`trainer.py`（单模型）与 `trainer_dual.py`（双路三阶段）仍保留各自的 `patience`。这两条线不在本文结果范围内，其早停基于验证集且仅涉及单一模型，不存在下述问题。

**原因一：触发条件过于苛刻，实际从未触发。**

早期实现要求**所有模型**连续 `patience` 轮均未刷新最佳方可停止：

```python
if PATIENCE and still and all(r.no_improve >= PATIENCE for r in still):
    break
```

而两个骨干的收敛速度差异显著——本轮训练中 ConvNeXt 至 **ep72** 仍在刷新最佳，DCNN 在 **ep59** 即已停止提升，二者相差 13 轮。`all()` 条件几乎不可能成立，80 轮训练中一次也未触发。**该机制在本项目的双模型场景下形同虚设。**

**原因二（更为关键）：早停与余弦退火存在冲突。**

`CosineAnnealingLR` 的 `T_max` 绑定于 `epochs`：

```python
cosine = (epochs - warmup_epochs) * steps_per_epoch
CosineAnnealingLR(optimizer, T_max=cosine, eta_min=base_lr * 0.01)
```

若早停于第 r 轮（r < epochs）触发，学习率仍停留在初值的 8%–15%，**无法走完退火尾段**。而最后的准确率增量恰恰来自该尾段——实测 DCNN 自 ep22 的 74.78% 提升至 ep59 的 99.41%，绝大部分增量发生在学习率衰减的中后段。

**因此正确的做法并非调整 patience，而是调整调度长度**：

```yaml
# 若需缩短训练时间，应修改此项；T_max 会自动跟随，余弦退火得以完整执行
epochs: 60        # 约 19.5 小时（batch 100 下约 19.5 分钟/轮）
```

配置中即使遗留 `patience` 键亦会被忽略，并打印提示信息。

```python
def _compute_page_acc(probs, sample_pages, page_to_true_label):
    page_votes = defaultdict(list)

        page_votes[page].append(probs[i])
    for page, char_probs_list in page_votes.items():
        page_avg_prob = np.mean(char_probs_list, axis=0)
        pred_label = np.argmax(page_avg_prob)
```

| v1.0 | `aaa3f966b7e09bc4` |

二者**逐字相同**。测试集亦为同一批 1019 页（页面名交集 1019，差异 0/0）。

### 8.3 置换检验

将"页面 → 书写者"映射随机打乱后：

```
打乱后 page_acc = 0.00% / 0.00% / 0.00%
原始      page_acc = 99.41%
```

结果降至 0（1019 页中未命中任何一页，理论期望同为 0–1 页），表明**标签映射正确，不存在泄漏**。

### 8.4 记忆判别

| | 伪字符级准确率 |
| :--- | ---: |
| 训练集（干净、无增强，抽样 6 万） | **30.21%** |
| 测试集 | **20.18%** |

**训练集准确率仅 30.21%，远未达到 100%，说明模型并未记忆训练集。** 测试集的 20.18% 属于诚实的泛化结果。

附带解释一处易引起困惑的现象：训练日志中的 `train_char_acc` 仅约 12%，原因是启用了 DropSegment 与坐标增强；关闭增强后即为 30.21%。增强使任务难度上升 18 个百分点，这是其应有作用。

### 8.5 独立脚本复现训练日志

`scripts/verify_page_metric.py` 从检查点重新执行完整前向推断，结果与训练日志完全吻合：

| | 训练日志 ep59 | 验证脚本 |
| :--- | ---: | ---: |
| char_acc | **20.18%** | **20.18%** |
| page_acc | **99.41%** | **99.41%** |

两位小数一致，可排除"训练阶段评测代码有误"的可能。

### 8.6 一处已修复的评测缺陷

`20-test` 记录表中的 `per_round_acc` 曾出现 **1.0196（超过 100%）** 这类不可能的值。

原因在于以公式 `indep_r = (r+1)·cum_r − r·cum_{r−1}` 反推每轮独立准确率——**该公式仅在"累积值等于各轮准确率的算术平均"时成立**，而实际累积值是对概率取平均后重新执行 argmax，属非线性运算。现改为直接记录当轮准确率。

> 影响范围：仅 `per_round_acc`、`round_mean_acc`、`round_std_acc` 三列。`final_cum_acc` 与 `cumulative_acc` 为直接计算所得，**结果不受影响**。

## 10. 工程实现

### 10.1 共享管道多模型训练

一份数据集、一个 DataLoader、多个模型同时训练：

```
📊 训练集样本数: 1168273（内存中只此一份）
🧠 [convnext] 参数量 5.616M
🧠 [dcnn] 参数量 2.609M
ℹ️  所有模型共享同一份内存数据与同一个 DataLoader ——
   特征提取每个 batch 只做一次，且各模型看到的增强样本完全一致。
```

**这保证双骨干对比构成严格的配对实验**：同一批增强样本、同一时刻、同一份内存张量。

### 10.2 切分结果的磁盘缓存

测试集是固定的，但每次建集都需重做三项高开销操作：读取上千个 `.wptt` 文件、逐页拐点检测、逐字符片段检测。

缓存落盘的是**坐标**而非特征图（特征图为 64×54×54 float32，约 746 KB/样本，测试集 29 万样本需 200 GB 以上；坐标整体仅需 100–400 MB）：

```
首次运行  16.07 秒（读取 + 拐点检测 + 切分）
再次运行   0.24 秒（直接加载）            —— 约 67 倍
```

- 缓存键包含 `STATIC_FEATURE_VERSION`，算法变更后旧缓存自动失效
- 坐标拼接为一个大数组并记录偏移量，加载后以切片视图共享内存
- 缓存目录不可写时降级为跳过缓存继续运行，不影响建集

### 10.3 平台自适应的多进程上下文

```python
MP_CONTEXT = 'fork' if sys.platform != 'win32' else None
```

`fork` 在 Linux 下更快（worker 启动几乎瞬时，内存占用低 30%–50%）；Windows 无 `fork` 系统调用，回退至平台默认值。该选择对训练结果无影响——PyTorch 的 `worker_init_fn` 会按 `worker_id` 重新设置随机种子，DropSegment 的随机性完整保留。

### 10.4 检查点与续训

- 每轮保存组合检查点（模型 + 优化器 + 调度器 + epoch）
- 刷新最佳时额外保存 `*_best.pth`
- 续训前校验 `static_feature_version`，不匹配则拒绝加载（避免旧特征权重配新特征）
- 全新训练时旧日志自动备份为 `.bak_<时间戳>`，不与新数据混合

### 10.5 日志

每轮写入 CSV，每个模型 14 列：

```
stage, train_loss, train_char_acc, train_char_top5, test_char_acc,
test_char_top5, page_acc, page_acc_top5, best_page_acc, is_best,
lr, lr_static, grad_norm, gpu_mem_peak_mb
```

训练结束后自动执行 20-test，并写出 `20test_summary.csv` 与 `<group>_20test_records.csv`。

## 11. 性能开销与硬件建议

**核心结论：本项目的瓶颈完全位于 CPU 侧的串行数据流水线，而非 GPU。** 选择机器时应关注单核性能与内存容量，显卡性能并非决定因素。

### 11.1 单轮训练的计算构成

一轮需处理 **1,168,273 个伪字符**，每个样本的 `__getitem__` 均包含一串**串行**操作：

| 步骤 | 操作 | 可否并行 |
| :--- | :--- | :--- |
| 1 | `apply_drop_segment_from_segments`（DropSegment） | 串行（按片段顺序重组轨迹） |
| 2 | `_augment_points`（坐标域平移 / 旋转 / 缩放） | 矩阵运算，单样本内串行 |
| 3 | `detect_corners` ×2（页面级 + 字符级） | **逐点扫描**，依赖前后 k 个点 |
| 4 | `pseudo_segment`（按宽度累加切分） | **串行累加**，达阈值即断开 |
| 5 | `cv2.polylines` 逐段绘制位图 | 单线程绘图 |
| 6 | `signatory.signature` ×（点数） | **5 阶迭代积分，逐点递推** |
| 7 | `cv2.dilate` + `cv2.equalizeHist` ×64 | 单线程（已调用 `cv2.setNumThreads(0)`） |

**上述操作在单样本内部完全无法并行**，16 个 worker 只是将不同样本分配至不同核心。因此：**提升吞吐量的唯一有效途径是提高 CPU 单核性能**，增加核心数、扩大显存或更换更高端 GPU 均无实质帮助。

### 11.2 实测开销

| 项 | 实测值 | 说明 |
| :--- | :--- | :--- |
| 单轮训练 | **16.6 分钟** | 11,683 步 × batch 100 |
| 单轮评估 | **约 4.5 分钟** | 测试集 292,838 个伪字符，两模型共享 |
| **单轮合计** | **约 21 分钟** | |
| 80 轮总计 | **约 28 小时** | 训练 22.1 h + 评估 6 h |
| 等数据时间占比 | **9%** | 主要来自宿主机资源竞争（ep8–13、ep39–46 两段） |
| `it/s` | 12.2 ~ 12.8 | 稳定区间 |
| **显存峰值** | **3.0 GB**（中位 1.45 GB） | batch 100 |
| 显存峰值（对照） | 5.4 GB | batch 192 |

**显存占用仅 3 GB，8 GB 显卡即可满足。** 但显存并非瓶颈，并不意味着显卡性能无关——`it/s` 中仍有一半时间用于前向与反向传播，**更换更快的显卡可缩短计算部分的耗时**，只是收益不如提升 CPU 明显。

### 11.3 硬件配置建议

| 部件 | 最低要求 | 推荐 | 理由 |
| :--- | :--- | :--- | :--- |
| **CPU 单核性能** | — | **尽可能高**（现代 EPYC / 至强 / 高主频桌面处理器） | **最关键的一项**。串行链路决定整体速度，低主频旧架构即使核心数充足，也会导致 GPU 长期处于空闲等待状态 |
| CPU 核心数 | 8 | **16–18** | 与 `num_workers=16` 匹配；实测 18 vCPU 下 16 worker 为最优值（继续增加会因上下文切换而变慢） |
| **内存** | **48 GB** | 64 GB | batch 100 下 48 GB 可运行；**若增加 `num_workers` 必须同步增加内存**（见 11.4） |
| **GPU 显存** | **8 GB** | 12 GB 以上 | batch 100 实测峰值仅 3.0 GB |
| GPU 性能 | — | **越高越好** | 可缩短前向与反向传播时间，但非主要瓶颈 |
| 磁盘 | 30 GB | 50 GB 以上 | 原始数据 + 切分缓存（训练 401 MB / 测试 100 MB） |

> **本次实测环境**：AMD EPYC 9754（18 vCPU）+ 60 GB 内存 + RTX 4090 D（24 GB）+ Ubuntu 22.04。
> batch 由 192 降至 100 之后，**48 GB 内存即可稳定运行**，无需 60 GB。

### 11.4 增加 num_workers 必须同步增加内存

每个 DataLoader worker 均为**独立进程**，`fork` 时复制数据集对象（坐标缓存为共享只读页，但 Python 对象头部及各 worker 的临时缓冲为私有）。

本数据集（1.17 M 个伪字符）下的粗略关系：

| num_workers | 内存需求 | 说明 |
| ---: | ---: | :--- |
| 8 | 约 40 GB | 保守配置 |
| **16** | **约 48 GB** | 本次实测配置 |
| 24 | 约 60 GB | 需 64 GB 机器 |
| 32 | 约 75 GB 以上 | 收益已被上下文切换抵消，不建议 |

**若希望通过增加 worker 提升速度，须先确认内存充足。** 内存不足时不会表现为"变慢"，而是被 OOM Killer 直接终止——实测在 60 GB 机器上使用超过 16 个 worker 会触发 `Killed`。

反之，**16 worker 配合 18 核已基本占满 CPU**，继续增加 worker 的边际收益很低（v2.0 时期实测：14→6.2 it/s、16→6.5 it/s、18→6.2 it/s，超过 16 反而更慢）。

### 11.5 三项关键优化

若需在其他机器上复现该速度，以下三项必须正确配置：

| 项 | 未配置的后果 |
| :--- | :--- |
| **切分结果缓存**（本仓库已内置） | 每次建集重做 4073 页的拐点检测、切分与片段索引；缓存命中后由 16 秒降至 0.24 秒 |
| **`multiprocessing_context='fork'`**（Linux） | Windows 无 fork，只能使用 `spawn`：每个 worker 需重新导入 numpy / cv2 / torch / signatory，启动时间增加 3–5 秒/个，单轮慢 30%–40% |
| **`cv2.setNumThreads(0)`** | OpenCV 会在每个 worker 内部再开启 18 个线程，形成 16×18 = 288 线程竞争 18 个核心，造成严重超订 |

> 本仓库已按平台自动选择上下文（Linux/macOS 使用 `fork`，Windows 使用平台默认值），并在 `dataset.py` 顶部调用 `cv2.setNumThreads(0)`。

## 14. 已知局限

以下逐项列出，供后续工作参考。

1. **未划分独立验证集。** 测试集同时用于每轮评估与最佳权重选择，所报告的 99.6% / 99.4% 存在乐观偏差。本轮最佳与末轮相差极小，但这不构成方法学保证。
2. **协议与原论文不可比。** 1019 vs 187 类、4 vs 2 训练页、自由 vs 固定内容测试页，三项差异均有利于本仓库。**唯一可直接比较的参照是 v1.0 的 95.09%**（同一划分、同一测试集、同一评测代码）。
3. **v1.0 的 95.09% 未在本仓库复现。** 该成绩系在拐点检测阈值与坐标量级不匹配、DropSegment 从未生效、伪字符退化为扁行的条件下取得。数值本身真实获得过，但以 A0 流水线自零重训无法达到（ep36 仅为 58.00%，当时的训练配置已不可考）。因此本文将其作为已知的历史结果引用，不做重复复现。
4. **20-test 在本数据上未带来增益**（−0.1 ~ −0.2 个百分点）。论文的 "markedly improved" 结论在 99% 量级上并不适用。
5. **伪字符级存在固有上限。** 单字符仅承载约 32 个点，本不足以在 1019 位书写者中唯一确定身份；实测训练集干净 char_acc 亦仅 30.21%，说明并非欠拟合。若需质变，应提供更多上下文而非增加算力。
6. **切片粒度与论文不同。** 论文举例为"3 笔汉字含 9 个片段"，本仓库的拐点检测仅给出中位 4 个，受限于数据采样密度（每笔画 13.7 点）。DropSegment 的 `m′ ≫ m` 前提在本数据上并不严格成立。
7. **ConvNeXt 的梯度范数持续上升**（ep80 达 74.7，DCNN 仅 10.0）。若训练更长轮次，需加强梯度裁剪或降低学习率。
8. **拐点检测仍为单一尺度二阶差分。** 论文采用的是弯曲值（多尺度）。本仓库实现过论文风格的多尺度弯曲值，在本数据上片段数仍为 3–4，说明瓶颈在于数据密度而非算法。
9. **早停不可用。** 已移除，原因见 [§7.3](#73-关于早停已从共享管道训练器移除)——该机制在本项目的双模型场景下从未触发，且与余弦退火存在冲突。需缩短训练时应调整 `epochs`。
